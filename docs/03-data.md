# Data: processing, policies and access

## Data processing

### Principle: flag instead of silently fixing

1. **Original files are never modified.** All output goes to `data/processed/`.
2. **Only unambiguous problems are corrected**, such as a typo. Otherwise the original value is
   kept, and the problem is exposed through **derived columns and flags** that the agent uses.
3. **Every decision is auditable.** Each problem found is recorded with table, record, rule,
   severity and action taken, all gathered in
   [`data/processed/data_quality_report.md`](../data/processed/data_quality_report.md).

The CSVs are read as plain text (`dtype=str`) and every type conversion is done and validated
explicitly. Invalid values are nulled and recorded, instead of breaking the pipeline or being
silently converted by pandas.

### Decisions by table

| Table | Problem found | Decision | Why |
|---|---|---|---|
| **products** | In 7 products (IDs 135–144), the description names another manufacturer (e.g. "Music Man Bass" described as "Fender Jazz Bass") or contradicts the specs (5 strings vs. 4; 88 keys vs. 61) | Conflict detected automatically by brand, characteristic model ("Precision" means Fender) and numbers. The original description is kept in `description_original`, `description` is generated from the specs and `description_verified=False` | We cannot know which field is right. The name is what customers ask for ("how much is the Yamaha Bass?") and the specs are structured, so they are the most reliable sources. A generic, correct description beats a rich, wrong one |
| | The `specs.strings` field has two meanings: string type (`"nylon"`, `"steel"`) for acoustic guitars and ukuleles, string count (`"4"`, `"6"`) for electric guitars and basses | Split into `string_type` (nylon/steel) and `string_count` (integer). Other numeric and boolean fields are converted too | Enables correct filters, such as "nylon-string guitars" or "5-string basses" |
| | Inconsistent status and stock: discontinued with 13 units (136), `coming_soon` with stock (130), active but out of stock (96) | New columns `availability` (`in_stock`, `out_of_stock`, `discontinued`, `coming_soon`) and `is_sellable`, true only for active products with stock | The manual (7.3) says discontinued products are no longer in the catalog and availability must never be confirmed without checking stock |
| | "Giannini GN-15 Nylon **Cedr** Natural" (84) | Corrected to "Cedro" through an explicit dictionary, applied only if the original name matches exactly | Unambiguous correction |

The current price is computed in the pipeline (`promotion_price_brl`, `pix_price_brl`) | Manual 6.2: promotions do not stack and the PIX discount (5%) does not apply to promotional prices. | **orders** | The recorded total differs from the sum of items in orders 3 (R$ 48 less) and 20 (R$ 88 less) | The recorded total is **kept**. The difference goes to `total_divergence_brl` | An order is a historical record: the amount charged may include discounts or old prices. The agent reports what was charged |
| | Installment plans that break the policy: orders 9 and 16 (6x below R$ 80) and 18 (12x of R$ 38) | `payment_method` is split into `payment_type` + `installments`; `installment_plan_valid=False` marks those cases | The agent must not use these orders as a precedent for payment terms |
| | Product 130 is `coming_soon` but was already sold and delivered (order 3) | Flagged as an outdated product status | No basis to decide which information is right |
| | Consistency between status and tracking, tracking code format (BR + 9 + BR) and dates | Validated. The current data breaks none of these rules | — |
| **customers** | Customers 11 and 43 share the same e-mail. There are possible duplicate names ("Diego Fernandes Castro" / "Diego Castro") | No automatic merge. Phone and e-mail are normalized (`phone_digits`, `email_normalized`) | LGPD: an e-mail alone does not identify the customer. ## Interpretations of the policy manual

The manual contradicts itself in places. The computable rules (installments, shipping,
deadlines) and the interpretation chosen for each conflict are centralized in
[`src/emporio/policy_rules.py`](../src/emporio/policy_rules.py). This module is used both by the
pipeline, to validate orders, and by the agent.

| Conflict | Decision | Reason |
|---|---|---|
| Phone: (67) 3341-4444 (cover and 1.2) vs. WhatsApp (67) 3321-4500 (section 7) | (67) 3341-4444 | It appears twice, including in the company registration table |
| E-mail with and without an accent (`empóriodamusica`) | Without the accent | An accent in a domain is almost certainly an autocorrect error |
| Section 3 table ("minimum installment R$ 100") vs. the tiers in 3.1 | The 3.1 tiers apply | The specific rule prevails over the general one |
| "Up to 3x with no minimum (except below R$ 50)" | 2x and 3x require installments of at least R$ 50; 1x is always allowed | The only reading that gives the exception a meaning and keeps the 50 → 80 → 100 progression |
| Free shipping "above" and a fee "below" R$ 500: exactly R$ 500 has no rule | R$ 500.00 or more ships free | The interpretation most favorable to the consumer (Brazilian Consumer Code, art. 47) |
| Defect exchange within 30 days (4.2) vs. 90-day legal warranty (8.1) | Complementary rules: the store exchanges within 30 days; legal warranty up to 90 days, mediated by the store; then the manufacturer. Defect cases are escalated to a human | The store is jointly liable during the legal warranty |
| The "metropolitan region" for motorcycle delivery has no defined cities | Motorcycle delivery (R$ 35 or free from R$ 500) only in Campo Grande; other cities via Correios/Jadlog, priced at checkout | The other cities in the data are more than 200 km away; promising motorcycle delivery would be risky |
| Withdrawal and warranty deadlines count from receipt, but the data has no actual delivery date | Uses the date given by the customer; otherwise the estimated delivery date, and the reply says which date was used | Best available approximation, and transparent |
| The right of withdrawal applies to online purchases, but orders have no sales channel | All orders in the data are treated as online | All of them go through shipping and delivery |
| "More than 300 instruments" vs. 65 products in the data | The agent answers only with what is in the system | Manual 7.1: never give information without checking the system |

## Data access layer

The agent's tools query the data through
[`StoreRepository`](../src/emporio/repository/repository.py), which returns typed Pydantic models.

| Decision | Reason |
|---|---|
| **Fixed, parameterized queries instead of text-to-SQL.** The LLM picks the tool and the filters (category, price range, brand, string type, electronics…), and the code builds the query from fixed fragments and bound parameters | Removes SQL injection and hallucinated queries, and protects customer data. The cost is less flexibility for analytical questions, which are out of scope for customer service |
| **Read-only connection** (`mode=ro`) | The agent never changes data |
| **Tolerant text search:** accent-free normalization, word coverage, plurals ("violão"/"violões"), hyphens ("d28"/"D-28") and typos ("yamha") | Customers do not type the exact product name. Simple, tested rules are enough for 65 products; embeddings would be overkill here |
| **Name lookup includes out-of-stock and discontinued products** | To answer "it is out of stock, but we have these alternatives" (manual 7.3) instead of "not found" |
| **Price filters use the current price** (promotional, if any) | "Up to R$ 2,000" must include the Crafter HT-100, listed at R$ 2,399 and on promotion for R$ 1,967.18 |
| **An order is shown only with its number + the owner's e-mail or phone.** All data given must match, comparison is constant-time, and the reply is identical for "order does not exist" and "data does not match" | LGPD: reveals neither which orders exist nor third-party data. The `Order` model carries no e-mail or phone |
| **Database built on demand** (`open_repository` runs the pipeline if the SQLite file does not exist) | No extra manual step after cloning |
